TD-1 → TD-5: rebase o reset + cherry-pick

Caso realista con ramas encadenadas. TD-2 nace desde TD-1, TD-3 desde TD-2, y así sucesivamente. TD-1 recibe ajustes antes de entrar a main. Cuando TD-2 se actualiza contra main, todavía arrastra cambios de TD-1.

¿Qué significa “apunta a la anterior”?

TD-2 no parte directamente de main. Su historial incluye lo que ya existía en TD-1.

TD-2 contiene:

1. el punto base A
2. el commit de TD-1: T1
3. su propio commit: T2

Eso está bien mientras TD-1 todavía no haya sido integrado o modificado en main.

2. Se solicitan cambios en TD-1

Antes de hacer merge, TD-1 recibe ajustes. Representaremos la versión final como T1'.

TD-1 entra a main sin conflicto. Desde este momento, main ya contiene T1′, que es la versión actualizada de TD-1.

Pero TD-2 ya existía

TD-2 fue creada antes de esos ajustes y conserva su historia original:

A→ T1 antiguo→ T2 propio
Al cambiar el target de TD-2 a main, TD-2 todavía conserva T1 en su historial, aunque main ya contiene T1′. Por eso en el PR pueden seguir apareciendo cambios que realmente pertenecían a TD-1.

Esto es especialmente visible cuando TD-1 fue reescrita, squash-mergeada o sus commits finales ya no son exactamente los mismos hashes que conserva TD-2.

T1 es el problema: pertenece conceptualmente a TD-1, pero sigue apareciendo en el historial de TD-2.

Objetivo

Queremos que TD-2 quede conceptualmente así:

A→ T1′ / TD-1 integrado→ T2
Es decir: main actualizado + solamente los cambios propios de TD-2.

Tienes dos estrategias comunes:

♻️ Rebase TD-2 sobre main

🍒 Resetear TD-2 a main y cherry-pickear sus commits propios

4. Solución A: rebase con main

Git intenta volver a aplicar los commits de TD-2 encima del main actual.

main
A
T1′
TD-2
T1
T2

Simulación

1. fetch: traemos el estado nuevo de origin/main.
2. rebase toma los commits de TD-2.
3. Git intenta reaplicar el T1 antiguo sobre main, pero main ya contiene T1′. Si los cambios no son equivalentes, el rebase se detiene con un conflicto.
4. Resolvemos T1: en el archivo dejamos la versión correcta T1′ que ya está en main, eliminamos los marcadores de conflicto, ejecutamos git add <archivo> y luego git rebase --continue. Así evitamos volver a introducir el T1 antiguo.
5. Después Git continúa con el commit propio de TD-2. T2 se reaplica sobre T1′ y pasa a ser T2′.
$ git fetch origin $ git switch TD-2 $ git rebase origin/main
Si el rebase se detiene en T1: abre el archivo en conflicto, conserva los cambios correctos que corresponden a T1′ de main, elimina los marcadores <<<<<<<, ======= y >>>>>>>, luego ejecuta git add archivo y git rebase --continue. Para cancelar: git rebase --abort.

5. Solución B: reset + cherry-pick

Esta opción es muy clara cuando puedes identificar exactamente qué commits son propios de TD-2.

Primero guarda el hash de T2 o crea una rama backup. Luego haces que TD-2 sea idéntica a main y finalmente vuelves a aplicar T2.
main
A
T1′
TD-2
T1
T2

Comandos

$ git fetch origin $ git switch TD-2 # seguridad $ git branch backup/TD-2 # guardar el hash propio de TD-2 $ git log --oneline Pulsa “Siguiente paso”...
Importante: reset --hard elimina del working tree los cambios no guardados. Haz commit/stash o backup antes.

La idea es siempre la misma: resetear la rama sobre su padre ya corregido y recuperar únicamente su commit propio con cherry-pick.

Simulación paso a paso

1. TD-3: partir de TD-2 corregida y recuperar T3.
2. TD-4: partir de TD-3 corregida y recuperar T4.
3. TD-5: partir de TD-4 corregida y recuperar T5.
4. Cadena final completamente actualizada.
$ Empezamos por TD-3... Pulsa “Siguiente rama”.

TD-3

$ git fetch origin $ git switch TD-3 $ git branch backup/TD-3 # ahora TD-3 parte de TD-2 corregida $ git reset --hard origin/TD-2 # recuperamos solo su cambio propio $ git cherry-pick <hash-T3> $ git push --force-with-lease origin TD-3

TD-4 y TD-5

# TD-4 $ git switch TD-4 $ git branch backup/TD-4 $ git reset --hard origin/TD-3 $ git cherry-pick <hash-T4> $ git push --force-with-lease origin TD-4 # TD-5 $ git switch TD-5 $ git branch backup/TD-5 $ git reset --hard origin/TD-4 $ git cherry-pick <hash-T5> $ git push --force-with-lease origin TD-5
Resultado final:
main: A → T1′
TD-2: A → T1′ → T2′
TD-3: A → T1′ → T2′ → T3′
TD-4: A → T1′ → T2′ → T3′ → T4′
TD-5: A → T1′ → T2′ → T3′ → T4′ → T5′
Si una rama tiene varios commits propios, debes cherry-pickear todos esos commits en orden, no solamente uno.

7. ¿Rebase o reset + cherry-pick?

♻️ Rebase

Mejor cuando: TD-2 tiene varios commits propios y quieres conservarlos como una secuencia.

Ventaja: Git reaplica tu trabajo sobre main automáticamente.

Riesgo: si T1 y T1′ son versiones diferentes del mismo cambio, puedes tener que resolver conflictos.

$ git fetch origin $ git switch TD-2 $ git rebase origin/main $ git push --force-with-lease origin TD-2

🍒 Reset + cherry-pick

Mejor cuando: sabes con claridad que TD-2 tiene 1 o pocos commits propios y quieres eliminar completamente la historia heredada de TD-1.

Ventaja: el resultado es muy explícito: main + únicamente T2.

Riesgo: debes identificar correctamente todos los commits propios antes del reset.

$ git branch backup/TD-2 $ git reset --hard origin/main $ git cherry-pick <hash-T2> $ git push --force-with-lease origin TD-2
SituaciónRecomendación
TD-2 tiene varios commits propiosRebase suele ser más cómodo
TD-2 tiene un único commit propio fácil de identificarReset + cherry-pick es muy claro
La rama ya fue publicada en GitHubDespués de reescribir historia: push --force-with-lease
TD-3…TD-5 dependen de TD-2Actualizarlas en orden después de arreglar TD-2
